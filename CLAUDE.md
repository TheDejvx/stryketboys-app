# StryketBoys – Stryktipset coupon tracker

## Project
Flask + vanilla JS app for tracking the group's weekly Stryktipset **and Europatipset** coupons. A different "boy" uploads a screenshot of the coupon each week; the app decodes it into structured picks, tracks live results, and installs to the homescreen on iOS/Android.
- **Local:** `C:\Users\David\Desktop\Stryktipset\stryketboys-app\`
- **Run locally:** `python app.py` → http://localhost:5003
- **Gotcha (Windows/Git Bash dev env):** backgrounded `python app.py` runs pile up as orphaned processes still bound to port 5003 across many test iterations in one session — `ps`/`pkill` inside Git Bash show MSYS-internal PIDs that do **not** match the real Windows PIDs, so `pkill -f "python app.py"` silently fails to kill them and new requests intermittently hit stale zombie processes (wrong code, wrong/missing env vars — this cost real time chasing a phantom "env var not working" bug that was actually a 10-zombie-process pileup). To actually clean up: use PowerShell — `Get-Process python | Stop-Process -Force` — and verify with `Get-NetTCPConnection -LocalPort 5003`, not Bash's `ps`/`netstat`.

## Stack
- Backend: Python/Flask, served with Waitress on Railway
- Frontend: Single-page HTML/JS (`templates/index.html`), no build step
- Data: MongoDB Atlas (`stryk_app` database, `stryk_state` collection), fallback to `stryk_data.json`
- Live draw data: `https://api.spela.svenskaspel.se/draw/1/{product}/draws` (public, no auth) — same API family/shape for both `stryktipset` and `europatipset`, just a different URL segment — no scraping needed
- Coupon decode: Gemini API (`google-genai`, `gemini-3.5-flash`), plain-text response parsed by regex (see decode-flow history below)
- Deploy: Dockerfile + `railway.json`, no Playwright/browser deps needed

## Data model (`stryk_data.json`)
```json
{
  "boys": ["Name1", "Name2", ...],
  "weeks": [
    {
      "id": "week-stryktipset-4970-...",
      "product": "stryktipset",
      "draw_number": 4970,
      "uploaded_by": "Name1",
      "system_type": "M-system",
      "rows": [
        {
          "row_num": 1, "home": "Sunderland", "away": "Arsenal",
          "match_id": 93093, "match_start": "2026-09-12T21:00:00+02:00",
          "kickoff_time": "Idag 21:00",
          "picks": ["1", "2"],
          "settled_result": null
        }
      ],
      "created_at": "..."
    }
  ]
}
```
- `picks` is always an array — length 1 for straight bets, 2-3 for garderade/system rows (M-system, B-system, etc). A row counts as correct if `settled_result` is present in `picks`.
- `settled_result` is filled in once a match finishes — either auto-derived client-side from the live draw API's `match.result` field (schema unverified — see caveat below), or manually tapped in by whoever's checking (finished rows always show a manual 1/X/2 override picker as a safety net).
- `users` drives login accounts. Each user: `{username, display_name, password_hash, must_change_password}`.
- `product` (`"stryktipset"` or `"europatipset"`) is required on every week — weeks are matched to a product's current draw by `product` **and** `draw_number` together, since both products can have an open draw simultaneously (see "Kupong shows all active coupons" above).
- **Uploader rotation** (`uploader_rotation`: ordered list of usernames, `uploader_rotation_index`: 0-based pointer to whose turn it is) is explicit, group-set state — not derived from `weeks.length` like the original implementation was. That was fragile: deleting a test coupon, or one person uploading both products' coupons in the same week, silently shifted whose turn came next with no way to correct it. `nextUploader()` (frontend) just reads `users[find username at rotation[index]].display_name`; `advanceUploaderRotation()` moves the pointer forward by one, called once per successful coupon save (`confirmDecodePreview()`) and persisted via the normal `/api/save` path. `load_data()` (`app.py`) self-heals missing fields via `data.setdefault(...)` with `DEFAULT_UPLOADER_ROTATION` — no manual DB migration needed when this shipped to a production doc that predated these fields. This is a **suggestion only**, same as before — any logged-in user can still upload regardless of whose turn it "should" be (`uploaded_by` is always the logged-in session's name, `nextUploader()` only feeds the "Näst på tur" hint text and the default `uploaded_by` when nobody's logged in).
- **`renderUploaderSchedule()`** (bottom of the Kupong tab, `#uploader-schedule`) projects the next 10 rotation turns onto calendar dates for a quick "who's up when" glance. There's no real "one turn per week" clock in the data (rotation advances per coupon *save*, and a calendar week can see 0-2 saves across the two products), so this anchors on Stryktipset's own `reg_close_time` (its current draw's closing Saturday) and adds 7 days per subsequent turn — an estimate, labeled as such in the UI, not a guarantee synced to actual save events.

## Products (Stryktipset / Europatipset)
Added Europatipset as a second product alongside the original Stryktipset-only build — same Svenska Spel API family, same 13-row coupon shape, so almost everything just needed to become product-parameterized rather than rebuilt:
- Backend: `PRODUCTS = ('stryktipset', 'europatipset')`, `_draw_cache`/`_last_scraped` are dicts keyed by product, `fetch_draw(product)` takes the product as an argument, and `background_poller()` polls both every cycle. `/api/draw` and `/api/refresh-draw` take a `?product=` query param (defaults to `stryktipset` for back-compat).
- Frontend: `PRODUCTS`/`PRODUCT_LABELS` drive per-product state — `drawData`/`drawUpdated`/`drawResult` are objects keyed by product, loaded for both on `init()` and polled for both every 20s. There's no single "selected" product anymore (see "Kupong shows all active coupons" below) — `findEvent(matchId, product)` and every render helper take `product` explicitly rather than reading a shared global. `selectedProduct` still exists as a leftover single default (used only as a decode-response fallback that should never actually trigger, since the server always returns a detected `product`) — there used to be a manual product tab toggle (`renderProductTabs()`/`switchProduct()`), removed once auto-detection (below) made it redundant.
- **Product is auto-detected at decode time, not chosen by the user.** `POST /api/coupon/decode` no longer takes a `product` field at all — it fetches *both* products' live draws up front (`draws = {p: fetch_draw(p) for p in PRODUCTS}`), decodes the coupon with a product-agnostic prompt (`build_describe_prompt(expected_rows)` — the product name was only ever cosmetic framing text, irrelevant to reading the pill grid), then fuzzy-matches the decoded team names against *each* product's fixture list and picks whichever product scores higher in aggregate (sum of per-row `fuzzy_match_event()` scores) — see the `# Auto-detect which product` block in `decode_coupon()`. In practice this is a decisive, unambiguous win for the correct product (~13.0 vs ~6.0 out of 13 rows in testing — verified directly against real fixture data, not just synthetically) since a given week's two competitions never share team names. `expected_rows` for the prompt/row-count validation is derived from whichever product's live draw has more rows (both are 13 today, but this no longer assumes it). The frontend switches its active tab to match the detected product (`onCouponFileChosen()`) and shows "Identifierad som: {product}" in the decode preview for transparency — no manual override control was added, since a wrong detection would already show as every row failing to fuzzy-match (the existing `low_confidence` warning), which is a strong enough signal to just retry rather than needing a correction path.

## Odds shown next to each match
`buildWeekRows()` appends the current 1/X/2 odds (`ev.odds_1`/`odds_x`/`odds_2`, already parsed by `parse_odds()` in `app.py` from the draw API's `odds` object) to the existing `.match-meta` line (same small muted text as the kickoff time) — e.g. "Idag 21:00 · 1.98 / 3.65 / 3.45". Deliberately discreet (reuses the existing meta-text styling rather than a new element) and shown regardless of match state, though it's really only informative pre-kickoff. The API also has `favouriteOdds`/`startOdds` and `svenskaFolket` (public betting distribution %) that aren't stored/shown — only current odds made it into the data model.

## Live score + live correct/incorrect badge
`currentScore(ev)` (frontend) reads the `'Current'` entry from `match.result` (distinct from `deriveResultSign()`, which prefers `'Fulltime'` for final settlement — `'Current'` is the one expected to track the live score while a match is still in progress, though this specific distinction is itself unverified against a real live match, same caveat as below). The pick pills are colored off `effectiveResult` (`row.settled_result || liveSign`).
**Finished-match badge/row tint** (evolved over a few rounds of feedback, current state): a finished row's badge just says plain "Avslutad" (used to say "✓ Rätt"/"✗ Fel"; that distinction now lives in color, not text) in `badge-correct`/`badge-incorrect` green/red — and the *whole row* now also tints green (`tip-correct`) or red (`tip-wrong`, new) to match. `tipMiss = finished && effectiveResult ? !tipHit : false` — deliberately scoped to **finished only**; a still-live row that's currently trailing stays untinted red (no `tip-wrong`), just the bordered `outcome` pill box, since a live scoreline can still flip before full time and red-tinting it would read as a final verdict it isn't. Once finished, that ambiguity is gone, hence the tint being allowed then.

## Known caveat: no real match-minute data exists (confirmed, not just unverified)
`deriveResultSign()`'s score-based guess was verified against a real finished match — see "Official results & payout" below, now hardened to the confirmed real shape rather than guessing multiple possible field names.
Checked against a real live match (Ljungskile-Norrby, SecondHalf): Svenska Spel's draws API has **no match-clock/minute field at all** — `extract_live_minute()`'s whole guessed-key-name approach (`matchClock`/`clock`/`minute`/etc.) was removed from `app.py` since none of them were ever going to exist. All that's actually available is `sportEventStatus` (coarse period: `NotStarted`/`FirstHalf`/`Halftime`/`SecondHalf`/`Interrupted`/`Ended`) and `statusTime` (when that status last changed) — both now exposed as `status_time` on each event. `estimateMinute(ev)` (frontend) computes an **estimate** from elapsed wall-clock time since `match_start` (first half) or `status_time` (second half, offset +45), capped at 45/90 — explicitly not official data, will drift from the real minute whenever there's stoppage time. Told to the user directly before implementing (asked to confirm they still wanted an estimate shown, not real data) — they said yes, show it as "80'".
Also found via the same real-match check: `sportEventStatus` can be `"Interrupted"` (`status: "Avbruten"`) — a status neither `isFinished()` nor the original `isLive()` recognized, so an interrupted match fell through to the default "Ej startad" bucket, which is exactly wrong (the match *has* started, just paused). `isLive()` now recognizes `interrupted`/`suspended`/`abandoned`/`avbruten`; a new `isInterrupted(ev)` shows a plain "⏸ Avbruten" badge instead of `estimateMinute()`'s elapsed-time guess (which would just keep counting up wrongly while the match clock has actually stopped).
`extract_live_minute()` in `app.py` (feeds `event.live_minute`) is still an open guess: every field probed there (`matchClock`/`clock`/`eventTime`/`liveTime`/`minute`/`currentMinute`/`gameTime`, plus a nested `liveData`/`live` dict) has never been confirmed, since no *in-progress* match has been observed yet (only pre-kickoff `NotStarted` and post-match `Ended` — see below; nothing captured mid-match so far). If it comes back `null` during a real live window, inspect `/api/draw`'s raw event JSON directly on Railway and add the real key(s); the frontend already handles `live_minute: null` gracefully (just shows "🔴 Pågår" with no minute suffix), so this degrades safely either way.

## Official results & payout
Confirmed by fetching a real finalized past draw (`/draw/1/stryktipset/draws/4969` — Sept 2026 week 36, already settled):
- **Match status/result fields** (on `match` inside each `drawEvent`): `sportEventStatus` is `"NotStarted"` pre-kickoff, `"Ended"` once done (`status`/`statusId` mirror this in Swedish: `"Inte startat"`/`0`, `"Slut"`/`31`). `match.result` is an array of `{sportEventResultType, home, away}` — `deriveResultSign()` now matches on `sportEventResultType === 'Fulltime'` specifically (previously guessed via a regex against `type`/`period`, which didn't actually match the real field name and only worked by luck of array ordering) and reads `entry.home`/`entry.away` directly (previously tried several guessed key names).
- **Bug fixed**: `isLive()` used to match `/started/` against `sportEventStatus`, and `"NotStarted"` contains the substring `"started"` — so not-yet-kicked-off matches showed "🔴 Pågår". Fixed with `\b` word-boundary regexes, an explicit `notstarted`/`"inte startat"` exclusion, and (primary guard) comparing `match_start` against the current time before even checking status text.
- **A dedicated `/draw/1/{product}/draws/{drawNumber}/result` endpoint exists** — 404s until Svenska Spel fully finalizes the draw (all 13 matches done *and* verified; this can lag last-kickoff by hours, not necessarily same-day), then returns:
  - `result.events[]` — `{matchId, outcome: "1"|"X"|"2", outcomeScore: {home, away}, ...}` — the **official** sign per match, no score-guessing needed.
  - `result.distribution[]` — `{winDiv, winners, amount, name: "13 rätt"}` etc. — the real payout table. `winDiv` is 0-indexed from the top (`0` = 13 rätt, `1` = 12 rätt, ...) — `fetch_result()` converts this to `correct: 13 - winDiv` rather than parsing the `name` string (which round-tripped through non-UTF8-safe tooling with a mangled "rätt" during investigation — the `winDiv` field sidesteps that entirely). `amount` is a Swedish-decimal string (`"764705,00"`) parsed with the existing `parse_odds()` helper.
  - There is **no live/preliminary payout** — parimutuel payouts can't be computed until the pool and national winner counts are final, so nothing shows until real finalization; the frontend's payout banner shows an honest "fastställs efter alla matcher" pending state rather than faking a live estimate.
- **Backend** (`app.py`): `fetch_result(product, draw_number)` caches per product in `_result_cache`; `background_poller()` calls it once per product per poll cycle *only* until it succeeds for the current `draw_number` (no point re-polling a 404 that's about to become permanent-until-next-week, but also no point stopping until we actually have it). `_result_for(product, draw)` guards against ever handing back a stale finalized result for the wrong (new) `draw_number`. Exposed via `result` field on both `GET /api/draw` and `POST /api/refresh-draw`.
- **Frontend** (`templates/index.html`): `drawResult[product]` holds `{draw_number, outcomes, distribution}`. In `buildWeekRows()`, once a row's match `isFinished()`, the official `outcomes[matchId]` (if present) always wins over — and can silently correct — a prior score-derived or manual `settled_result`. `payoutBannerHtml()` returns "🏆 Nuvarande utdelning: X kr" (looked up by matching a week's current `correct` count against `distribution`) or a pending/no-win state; `payoutTableHtml()` renders the full 10/11/12/13-rätt table, highlighting whichever tier matches. Both are pure functions (return HTML strings, no DOM side effects) so they're reusable across every place a week can be shown (see below).

## Kupong shows all active coupons; Historik expands to full detail
Originally Kupong showed exactly one week (whichever matched `selectedProduct`'s current draw), and Historik was a flat list of compact rows with no detail view. Changed to: Kupong shows *every* not-yet-fully-settled coupon across *both* products at once (there can be 0, 1, or 2 simultaneously), and any Historik row can be expanded in place to show the same full detail (rows, live/final badges, payout) as Kupong.
- **`buildWeekRows(week)`** (`templates/index.html`) is the shared core: settles a week's rows against its own product's `drawData`/`drawResult` (mutating `settled_result` exactly as before) and returns `{rowsHtml, correct, wrong, pending, changed, allFinished}`. `allFinished` — true only if every row's match `isFinished()` — is the "active" test: a week is active iff `!allFinished`. This runs per-week now (not just for one "current" week), so it's the single source of truth both for which weeks are active and for their row markup, called from both `renderKupong()` and `renderHistory()`'s expand path — guaranteeing they never show different settlement state for the same week.
- **`weekCardHtml(week, built, opts)`** builds one fully self-contained card, in this order: Rätt/Fel/Kvar tally → the coupon card itself (header + draw-meta + rows) → payout banner → payout table. Payout deliberately sits *under* the coupon, not above it (was above originally; moved per feedback). Used for each active week on Kupong (`opts: {showRefresh: true, showDelete: true}`). The static HTML has no fixed `#kupong-title`/`#tally-bar`/`#payout-banner`/`#kupong-body` elements — `renderKupong()` just builds an array of card HTML strings (one per active week, plus an `uploadPromptHtml(product, draw)` card for any product whose *current* draw has no coupon uploaded yet — but not for a current draw whose coupon is already fully settled, which correctly just disappears from Kupong at that point) and sets `#kupong-list`'s `innerHTML` once.
- **A dedicated "re-upload a photo for an already-active coupon" box was tried and removed** — added a `replaceWeekId`-aware variant of `uploadPromptHtml()` under each active coupon, but it landed as visual clutter the group didn't want (asked to remove it directly). What stayed: `confirmDecodePreview()` unconditionally looks up whether a week already exists for the decoded `(product, draw_number)` and, if so, includes its `id` in the save payload — `save_coupon()` (`app.py`) already upserts by id (`week_id = payload.get('id') or <generated>`). So *any* upload for a draw that already has a coupon transparently replaces it rather than duplicating, without needing a dedicated UI element for it — correcting a bad photo is delete-then-reupload via the normal flow, same as before this feature existed.
- **Historik** (`renderHistory()`) keeps its existing compact list (still shows every week ever, active or not) but each `.week-card-header` is now clickable (`toggleWeekDetail(weekId)`, tracked in the `expandedWeeks` Set), rendering a `buildWeekRows()`-powered detail block — same payout banner/table/rows as Kupong, just without the refresh/delete controls in the detail body (delete is still available on the header itself, with `event.stopPropagation()` so it doesn't also toggle expand).
- Manual result entry (`setManualResult`) now takes `(weekId, rowNum, sign)` instead of implicitly operating on "the current week" (`currentWeek()`/`deleteCurrentWeek()` were removed — every action now targets an explicit week, since multiple can be on-screen at once). Likewise `manualRefresh(product, btnEl)` and file upload (`onCouponFileChosen(inputEl)`) now take explicit element/product references instead of assuming one fixed `#coupon-file`/`#upload-btn` pair, since there can be up to two upload prompts on screen simultaneously (one per product).

## Live polling & manual refresh
- No push/WebSocket API exists for this data (confirmed via search — Svenska Spel's draws API is undocumented/reverse-engineered, GET-only, no realtime channel). Live-ness is polling, tuned to feel closer to real-time without hammering the upstream API needlessly:
  - **Backend** (`background_poller()` in `app.py`): self-throttling interval — `LIVE_POLL_SECONDS = 20` if `has_live_match()` finds any event that's kicked off but not finished on either product's cached draw, else `IDLE_POLL_SECONDS = 90`. Checked fresh every cycle, so it speeds up automatically right as the first Saturday match kicks off and slows back down once everything's finished.
  - **Frontend**: `setInterval(() => loadDraw(selectedProduct), 20000)` — reads the server's already-cached draw (cheap, no upstream call), so 20s client-side polling is safe regardless of the backend's own cadence. `GET /api/draw`/`POST /api/refresh-draw` both now also return `has_live` (bool) in case that's ever needed client-side (not currently used — client just polls at a fixed cadence).
  - **Manual refresh**: 🔄 button next to the Kupong tab's draw-updated timestamp (`manualRefresh()`) forces an immediate `POST /api/refresh-draw` (bypasses both poll cycles) and shows a disabled ⏳ state mid-request.
- **Running tally is live, not just post-match**: `renderKupong()` now derives a *provisional* sign via `deriveResultSign(ev)` for any row whose match `isLive()` but not `isFinished()`, and folds it into the Rätt/Fel/Kvar counts and pill highlighting (`effectiveResult = row.settled_result || liveSign`) — without ever writing it to `row.settled_result`, since a live scoreline can still flip before full time. Once `isFinished()` flips true, the normal auto-derive-and-persist path takes over as before.

## Coupon decode flow
This went through several iterations to fix garderade (multi-sign, e.g. X2) rows getting under-read — worth knowing the history if it regresses again:
- **v1**: asked the model for a `picks` array directly via a forced tool call. It applied a "radio button" bias and frequently dropped the second sign.
- **v2**: split picks into three independent booleans (`one_selected`/`x_selected`/`two_selected`) in the same forced-tool-call schema. Marginal improvement at best — forcing `tool_choice` from the first token gives the model zero room to actually reason before answering.
- **v3**: two API calls — a free-text row-by-row reasoning pass, then a second call asking the model to transcribe that analysis into the structured tool schema. Only fixed some rows; the second call (an LLM re-summarizing its own prior output) was itself a plausible new place to lose detail.
- **v4**: single API call, free text row-by-row reasoning ending in a batched machine-readable `SUMMARY:` block (`ROW <n> | ...` per row) parsed by plain regex — no second LLM call, so nothing gets lost in transcription. Better, but real server logs (see below) caught it still failing on specific rows: the model's free-text analysis **silently skipped some rows entirely** (e.g. no "Row 5" write-up anywhere) and went out of order, yet the batched SUMMARY block at the end still confidently emitted a value for every row regardless — including ones it never actually analyzed. Batching the machine-readable output at the end let the final answer detach from the actual reasoning.
- **v5**: same single-call, no-second-LLM-call design, but the per-row `ROW <n> | ...` line must now be emitted **immediately after that row's own analysis, interleaved row-by-row**, instead of batched into one block at the end. This structurally fixed the v4 skipped-row bug — real server logs confirmed every row got its own analysis, in order, with its ROW line matching that analysis. But logs *also* showed the remaining failures were a different problem entirely: the model's own written analysis explicitly, confidently stated the wrong color for specific pills (e.g. "the 2 pill is white — not selected" for a pill that was actually navy-filled). That's a genuine vision-perception error, not a reasoning-structure problem — no amount of "think before you answer" prompting fixes a wrong observation.
- **v6**: tried having the model report **pixel coordinates** (width/height fractions) of each pill's center instead of judging color, then sampled real image pixels at those coordinates server-side with Pillow (`pill_is_selected()`, brightness threshold) — reasoning being that pointing should be easier than fine color discrimination. Logs proved this was worse, and revealed *why* precise coordinate-pointing doesn't work with this model at all: the reported y-coordinates climbed in a suspiciously perfect linear sequence (~+0.083 per row) sailing straight past 1.0 (off the image) by row 7 — the model was fabricating a plausible-looking arithmetic pattern, not actually measuring positions. General-purpose vision models are just not reliable at precise spatial grounding of small UI elements; abandoned this direction entirely.
- **v7**: back to direct 0/1 color judgment (like v5, whose row-by-row interleaved structure was sound), but the model is given **two images** in the same call: the full coupon screenshot (for team names/order) plus a deterministically-cropped and ~2.5x upscaled zoom of just the right-hand pills column, for judging pill fill color against much bigger, clearer pixels. Better (fewer wrong rows), but still wrong on some rows, *and* the row-skip bug from v4 resurfaced (a row missing from the analysis entirely again) even with v5's interleaved structure. The pills-only crop gave the model nothing to anchor row identity to between the two images — it had to count/cross-reference position, and a miscount would silently paste the wrong row's pills onto the wrong team names.
- **v8**: composite zoom — each row's printed row NUMBER pasted directly next to that same row's pills (same original y-coordinate), so the model reads a row's number and pills together in one glance instead of counting/cross-referencing against the full image. Reduced wrong rows further, but the v4 row-skip bug resurfaced (a row missing from the analysis entirely) and some rows were still misread — the model still had to hold "which of 13 near-identical rows am I on" in its head across one long response, and that itself seems to be a failure point independent of image clarity.
- **v9**: tried removing row-identity tracking from the model's job entirely — a coarse localization call to estimate row 1's and the last row's y-position, then code deterministically sliced each row's pills into its own isolated, upscaled crop and sent all 13 in a fixed guaranteed order (two sequential API calls, 14+ images). Structurally the most rigorous attempt, and it did work — but at real cost: ~2x the latency (two round-trips) and materially higher token/request cost per decode, for a decode that still wasn't reliably perfect.
- **v10 (current)**: rolled back to **v5** (single call, single image, direct 0/1 judgment, row-by-row interleaved analysis) — the fast, cheap baseline. After 9 rounds it became clear this is a genuine model-capability ceiling (fine-grained visual discrimination across ~39 small near-identical repeated elements), not a fixable bug — team names/kickoff times read correctly nearly every attempt across every version; it's specifically the pill grid that's hard, and more elaborate pipelines bought marginal accuracy at real latency/cost, not a solved problem. The actual reliability mechanism is now explicitly the **editable preview UI**, not the decode itself.
- **Per-row photo crops were attempted and abandoned** — worth knowing the full history so it isn't retried blind:
  - 2-point global estimate (`ROW1_Y`/`LASTROW_Y`, linearly interpolated across all 13 rows) — small estimation error compounded across the list, later rows visibly drifted onto the *next* row's photo.
  - Each `ROW` line reporting its own `Y` position instead — the theory was that team-name text should be more reliable than small pill colors. Still drifted in practice — the model's raw numeric coordinate output isn't reliably grounded in real measurement at all, regardless of how simple the target is.
  - A deterministic, non-AI pixel approach (detect the coupon's alternating row background shade via Pillow — collapse a horizontal strip to a 1px column, look for periodic color transitions), tested rigorously against synthetic images across several algorithm variants (peak-detection, windowed-diff, coarse-resize, matched-filter-grid-search) — none separated the true row-boundary signal from team-name-text noise reliably enough to trust blind, without the real photo to validate against.
  - A drag-two-lines-on-the-photo manual calibration (human-confirmed anchors, guaranteed correct) — technically worked, but the added UI complexity (per-row crops + calibration lines) wasn't worth it for what the feature bought; reverted at the user's call.
  - **Current (back to the pre-crop design)**: a single full-size photo of the upload — not per-row crops — rendered below the row list (`decodePreview.imageUrl`, `URL.createObjectURL(file)`) so the user can scroll and compare against the real coupon while correcting picks. Revoked via `releaseDecodePreviewImage()` on cancel/save to avoid leaking blob URLs. The decode prompt/schema has no `Y` field anymore — see `DESCRIBE_PROMPT`/`ROW_LINE_RE` in `app.py`, back to the plain v5 shape.
- **v11 (current) — switched model provider, not prompt**: after 10 rounds of Claude-side prompt/pipeline engineering (v1-v10 above) plateaued on what looked like a genuine model-capability ceiling, manually testing the same coupon photo directly against Gemini (outside this app) got the pill grid right on the first try. Swapped the decode call from Claude (`anthropic` SDK) to Gemini (`google-genai` SDK, `gemini-3.5-flash`, see `get_gemini()`) — same `DESCRIBE_PROMPT`/`ROW_LINE_RE`/`parse_decode_analysis()` contract unchanged, since the plain-text-then-regex approach doesn't care which model produced the text. Different vision encoders evidently have real, different strengths on this specific fine-grained-repeated-grid task — worth remembering next time a vision task stalls: cross-provider comparison is a cheap, high-signal experiment, not just prompt iteration on one model. `ANTHROPIC_API_KEY` / `anthropic` dependency were fully removed; `GEMINI_API_KEY` is now required for decode to work. Note: `gemini-2.5-pro` returned a 404 in production ("no longer available to new users, use gemini-3.1-pro-preview") despite being documented as current — trust the live API error over docs/search results for the exact model ID. `gemini-3.1-pro-preview` in turn hit a free-tier quota of 0 (Pro-tier models aren't included in the free API tier at all, only Flash is) — confirmed via a standalone test script hitting the real key directly, not through the app, since local Flask testing here has repeatedly been unreliable (see next note). Landed on `gemini-3.5-flash`, which the same direct test confirmed works on the free tier and reads images correctly.
- The raw analysis text is printed to server logs (`railway logs`) on every decode call specifically so a bad read can be diagnosed against real data instead of guessing blind — this is exactly how every one of the v4–v9 root causes above were actually found, not by continuing to guess at prompt wording. `PYTHONUNBUFFERED=1` is set in the `Dockerfile` — without it, `print()` output never reached Railway's log capture at all.
- If a row parses with zero picks, it's flagged `low_confidence` (every real coupon row has ≥1 pick, so an empty read is itself a decode error). A parsed row count other than exactly 13 is a hard error asking the user to retry the upload — never silently save an incomplete coupon.
- Backend fuzzy-matches each decoded row's team names against the current live draw (`difflib.SequenceMatcher`) to attach `match_id`; rows that don't clear a 0.55 similarity threshold are also flagged `low_confidence` and highlighted in the review UI.

## Endpoints
- `GET /api/data` / `POST /api/save` — load/save the whole state blob (Mongo w/ JSON fallback). `GET` strips `password_hash` via `public_data()`; `POST` re-merges each user's existing hash by username if the client didn't send one, so a stale client blob can never wipe a password.
- `GET /api/draw` / `POST /api/refresh-draw` — `?product=stryktipset|europatipset` (defaults to `stryktipset`) — cached current draw for that product (matches, odds, live status, `has_live`), background-polled every 20s while a match is live, else every 90s (see Live polling section below). Also returns `result`: `null` until Svenska Spel finalizes the draw, then `{draw_number, outcomes: {matchId: "1"|"X"|"2"}, distribution: [{correct, winners, amount}]}` (see Official results & payout section below).
- `POST /api/coupon/decode` — multipart `image` field only → structured preview including auto-detected `product` (not persisted)
- `POST /api/coupon/save` — persist a confirmed week, `product` included in the JSON payload
- `POST /api/login` — `{username, password}` → `{status, username, display_name, must_change_password}`. Username match is case-insensitive.
- `POST /api/change-password` — `{username, current_password, new_password}`, requires the current password to verify, clears `must_change_password`.

## Statistik tab
All four sections gate on `isWeekFullySettled(week)` (every row has a `settled_result` — i.e. `weekTally(week).total === week.rows.length`) before counting a week toward averages or the perfect-score list, specifically so a still-live week's partial tally can't skew things downward.
- **Snittresultat** (`renderGroupAverage`) — group-wide average correct count per settled week (not a %, a plain "9.2 / 13" — the row count itself is read off the first settled week, in case that ever isn't 13).
- **Senaste resultat** (`renderRecentResults`) — last 10 weeks (any state, not just settled — an in-progress week shows "(pågår)"), newest first: uploader + product/draw + tally.
- **Maraton** (`renderMarathon`) — ranked list by average correct-per-settled-week per uploader (`computeBoyStats()`: `correctSum / weeksSettled`), not by aggregate accuracy % like the old "Statistik per gubbe" grid it replaced — "flest rätt i snitt" is specifically about per-week average, a different number than lifetime pick accuracy.
- **13 rätt-klubben** (`renderPerfectWeeks`) — every fully-settled week where `correct === total` (a full sweep of however many rows that week had, not hardcoded to 13, though that's what it'll be for a normal coupon).

## Accounts
Six accounts, seeded via `seed_users.py` (rerun it to reset everyone's password — it overwrites the whole `users` list, preserving `weeks`): username = first name, initial password = surname (lowercase). Every account starts with `must_change_password: true`; the frontend's login modal forces a password-change step before granting a session — it withholds `setSession()` until that completes, so there's no way to end up logged in while still on the seed password. Sessions live in `localStorage` (`stryk_session`) for 30 days. Viewing the app (Kupong/Historik/Statistik) needs no login; uploading a coupon or manually setting a `settled_result` does, and attributes the action to whoever's logged in — no more free-text uploader picker.
- **`last_login`** — stamped (UTC ISO) on each user in `/api/login` (`app.py`), persisted via the normal `save_data()` path. Rides along in `public_data()`'s user projection (technically present for every user in `/api/data`, same trust level as everything else in this friend-app's session model) but the frontend (`renderMyLastLogin()`) deliberately only ever renders the *currently logged-in* user's own value — a quiet "Senast inloggad: ..." line at the very bottom of the Kupong tab, nothing shown for anyone else. Explicit ask: track it, but don't surface who's been logging in to the group at large.

## PWA install
Unlike the sibling `vm-app` (whose service worker is never registered and has no manifest — install there is just a bookmark), this app ships a real `manifest.json` + registered `static/sw.js` + `apple-touch-icon`, so "Add to Home Screen" produces an actual installed app icon on both iOS and Android. Icons are generated via `gen_icons.py` (Pillow) from `static/logo-source.jpg` (a group-provided AI-generated badge/logo, wide aspect ratio with the circular emblem centered) — the script center-crops it square and resizes to `icon-192.png`/`icon-512.png`/`icon-180.png`. Originally these were a procedurally-drawn navy "SB" monogram; replaced with the real logo. Rerun `python gen_icons.py` if `logo-source.jpg` changes — no other file needs touching, `manifest.json`/`index.html`'s `<link>` tags already point at the same filenames. The logo also appears in the app header (`.app-logo`, next to the "StryketBoys" title) as the one on-page brand placement — deliberately just the one spot, not scattered throughout.

## Edit-lock
Superseded by real per-user accounts (see Accounts above) — unlike `vm-app`/`gc-app`'s single shared hardcoded password, this app has individually distinguishable, server-verified logins. Still friend-app-grade security, not enterprise auth: sessions are just a client-trusted `{username, display_name}` blob in `localStorage`, not a signed token, so a motivated group member could forge who an action is attributed to. Good enough for a trusted friend group; would need real session tokens if that trust model ever changes.
